# Introduction

## Objective

This repository provides a dynamic, AI-maintained documentation library for the Air Quality
(AQIE) service estate.

## Scope

- Documentation-only repository
- No service source code
- No secrets or sensitive data — environment variable names only
- Standardised service descriptions
- Standardised update and interrogation process

## How it is structured

| Layer | Artefact | Maintained how |
|---|---|---|
| Structure | [`/docs/integration-catalog.yaml`](integration-catalog.yaml) | Hand-curated from code evidence |
| Metadata | [`/docs/repository-catalog.yaml`](repository-catalog.yaml) | Generated by script from the GitHub API |
| Detail | `service-profile.md` per service | Written from source analysis |
| Visuals | [`/docs/diagrams/generated/`](diagrams/generated/README.md) | Generated from the integration catalogue |
| Narrative | [`/docs/master/system-landscape.md`](master/system-landscape.md) | Written, informed by the above |

The integration catalogue is the source of truth. Diagrams and `connected_services` are
derived from it, so they cannot drift from it.

## Core documentation requirements

Every service profile covers:

1. Service metadata, including the commit it was analysed at
2. Purpose and responsibilities, including explicit scope boundaries
3. Architecture pattern and component map
4. API surface exposed
5. Outbound dependencies, with the data exchanged
6. Inbound dependencies
7. Data stores, entities and retention
8. Configuration — variable names only
9. Hosting and deployment
10. Observability
11. Open questions

## Evidence standard

Every integration claim cites a repository, file and line on the default branch. Test
fixtures and mock URLs are not evidence. Claims that were investigated and disproved are
recorded under `refuted_edges` rather than deleted, so they are not reintroduced.

## Standard repository metadata

- Repository URL, default branch, primary language
- `created_at_utc`
- `last_modified_at_utc`, derived from default-branch head commit
- `activity_status` — `Active` / `Monitoring` / `Inactive` / `Archived`
- Type classification from the taxonomy
- `connected_services`, read from the integration catalogue
- `documentation_path`

## Service domains

- **Citizen** — citizen-facing interfaces. Present data, own none.
- **Data** — own data or broker access to it.
- **Shared** — test and performance harnesses, and repositories that fit neither domain.

Each domain has an overview document indexing its services, and one folder per service
containing a `service-profile.md`.

## Status

Documentation is derived from static analysis of public `main` branches and has not yet
been reviewed by service owners. Open questions are tracked in the integration catalogue.
